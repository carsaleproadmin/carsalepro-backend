# CLAUDE.md — CarSalePro Backend

Agent-specific guidance. Project overview, stack, endpoints, and run/deploy steps are in `README.md` — read it first, and don't duplicate it here. It is deliberately NOT an @-reference: that loaded all 18 KB of it into every session, including the ones that never leave `src/`.

## What this repo is now

One NestJS service with **two API surfaces** (see `README.md`):

- **Legacy mobile MVP** — root routes (`/vin`, `/quota`, `/reports`, `/me`, `/catalog`, `/legal`, `/health`), `X-Device-Id` auth, **frozen contract** (the shipped Flutter app depends on it byte-for-byte).
- **Website (Phase 2+)** — `/api/v1/*`, Bearer-JWT auth. The full marketplace / inspection-exchange / payments / KYC / LegalSync / admin / notifications platform was **built in this repo** (extending it in place was a deliberate decision — do NOT suggest moving it to a separate repo).

## Reference catalog (`src/catalog/catalog.data.ts` + `src/catalog/i18n/`)

Single source of truth for `GET /catalog`, exported to the mobile bundle via `npx ts-node scripts/export-catalog.ts` (never hand-edit `carsalepro-mobile/assets/catalog/catalog.v1.json`).

**The catalog now carries all 35 app languages, 1 115 localizable entries each.** The four human-translated locales (`de`/`en`/`ru`/`uk`) stay authored by hand in `catalog.data.ts`; the other 31 live as one sidecar per locale in `src/catalog/i18n/catalog.<tag>.json` and are merged in by `mergeCatalogI18n` — at boot from `CatalogModule.onModuleInit`, and at export from the export script. Splicing 31 more fields into each of 1 115 label objects would have taken `catalog.data.ts` past 30 000 lines, buried its ~100 explanatory comments in machine output, and made the provenance of any given string invisible. `LocalizedLabel` is therefore an index signature over tags, not a fixed set of fields.

A sidecar key matching no catalog entry is **reported, never fatal**: the catalog is allowed to drop an entry between a translation run and an export, and failing the export over that would block a legitimate change. Orphans surface as a warning from both the module and the script.

**Why the completeness spec matters more than it looks.** Every label has a fallback chain on the client (`zh-Hant → zh → en`, `ms → id → en`, `uk → ru → en`), so a locale whose sidecar merged nothing renders a *different language* with nothing erroring anywhere. That is exactly how 164 Ukrainian catalog labels shipped as Russian in July 2026. `catalog.i18n.spec.ts` asserts that all 31 sidecars exist and that each covers every localizable entry; the mobile repo asserts the same over the exported bundle. The fallback is insurance, not evidence.

**The damage cost snapshot is data the backend stores and never computes.** Every money and hours field on `ReportDamageDto` is optional and arrives already frozen by the app, which is what lets a cost table be corrected without re-pricing a filed report. `blendHours` joined them on 2026-08-14 for the adjacent-panel refinish (*Beilackierung*): it travels separately from `paintHours` because BGH VI ZR 396/18 grants a blend only where the finish makes it necessary, so an assessor must be able to point at that figure alone. `estimateEur` is the engine's total BEFORE any manual override — a consumer that wants the printed figure takes `manualCostEur` when it is present.

**The three registers are 410 parts, 167 damage types and 232 repair methods, in EIGHT groups, and `g_general` carries `order: 1`.** The eighth group arrived on 2026-08-16 with the client's two "General" tables: 40 damage types and 27 repair methods that describe what happened to a part and what is done about it, not which part it is. Three rules come with it.
- **`signoff.obdDevice` (2026-08-17)** — the make and model of the diagnostic tool, free text, `@MaxLength(120)`. Additive and optional, like every field before it. `validateReportDataV1` runs with `whitelist: false`, so an app that sends a key this build does not know is NOT rejected — which is why no deploy ordering is forced for a new field, only for a new limit.
- **It holds no parts, and that is load-bearing.** The mobile picker does not render a group with no options in the register it is showing, so the PARTS picker is unchanged; and the app's free-text price is a median over damage × allowed method × parts **of the same group**, so 40 new damage types moved it by nothing. Give the group parts and both facts change.
- **Group `order` is the render order in all three pickers**, so the seven original groups moved to 2..8. Nothing in `lib/` hardcodes a group id, but the mobile cost-document generator numbers its sections from `order` — a literal section number there collides with the new group.
- **About twenty of the forty repeat a word a more specific entry already carries** (a dent, a scratch, corrosion, a crack). The client asked for the list exactly as sent. The app answers the duplication by dropping the tick that used to mark the group holding the current choice.

Each `ChecklistItemDef` carries `defaultTier` (T1/T2/T3) and `partId?` — the mobile app turns the 98 checks into damage presets and stores them as synthetic **`C<number>` codes** (e.g. `C42`) in `ReportDamageDto.kstCode` (`@MaxLength(8)`). **The `C` prefix is reserved for that mapping — never mint real K/S/T codes starting with `C`.**

**The 17 required exterior angles are ordered by the inspector's walk-around**, and the ORDER is a client deliverable, so `catalog.e2e-spec.ts` asserts it as a sequence and never as a set: down the left flank (`diag_front_left → left → diag_rear_left`), across the rear, open the luggage area (`trunk_open → trunk_left → trunk_right → trunk_tools`), round to the `front`, open the bonnet (`hood_open → engine_bay → hood_underside → engine_bay_left → engine_bay_right`), then down the right flank. It grew from 8 on 2026-08-10; the nine additions are the luggage area and the engine bay. **All seventeen carry a `hint`**, and 23 of the catalog's 40 angles do. The diagonal hint deliberately does not name a side: the longer RU/UK wording wrapped to a second line and pushed the mobile capture screen's instruction box past what a 320 dp screen can host at the 1.3 font clamp.

**The hints fall into FIVE families, and the difference between them IS the instruction** — so the e2e suite asserts the semantic split per locale and that the families do not collide, rather than counting hinted angles. Four of the original eight shipped with no hint at all until 2026-08-05, and their absence is still pinned in both repos.

| Family | Angles | Says |
|---|---|---|
| turn the near front wheel **inward** | the 2 FRONT diagonals | where to steer |
| wheels square | 4 straight views + the 2 REAR diagonals | where to steer |
| open or lift | the 9 angles of 2026-08-10 | what to open |
| sit on the rear seat | 5 cabin angles | where to stand |
| photograph the keys anyway | 1 cabin angle | what to shoot when the book is missing |

- **The front-diagonal hint says INWARD, not outward, since 2026-08-19.** `angles.diag_front_left.hint` and `diag_front_right.hint` read "Turn the near front wheel inward." (DE `nach innen ein`, RU `внутрь`, UK `всередину`). Turning the wheel *out* on a front three-quarter view hides the wheel face behind the arch and shows the tyre sidewall; turning it in presents the rim and the brake disc, which is what the angle exists to document. The two hints are **byte-identical to each other** for the same reason the rear pair is — one authoring decision, no second translation unit. `catalog.e2e-spec.ts` had an `outward` family constant and three `contains('outward')` assertions; all four moved with the string, so a revert fails a test rather than passing one.
- **The diagonal/straight boundary MOVED on 2026-08-17** at the client's request. On a rear three-quarter view the near front wheel is at the far end of the car and reads as a few pixels, so turning it out shows nothing and spoils the stance. `diag_rear_left` and `diag_rear_right` now hold the straight family's text **byte-identically** — deliberately the same string, because `extract.mjs` keys a unit on the text, so an identical value creates no translation unit in any of the 31 sidecars and a reworded near-duplicate would have cost 31 hand translations. The e2e suite asserts `hintOf('diag_rear_*')` equals `hintOf('left')` exactly. The client reported the right-hand angle; the mirror had the same defect and was corrected with it.
- **`angles.hood_underside.hint` reads "Take it from below." since 2026-08-17**, and the fault that let its predecessor ship was in the GUARD, not in the word. It said "Shoot it from below." and the machine output meant FIRE A WEAPON in at least eleven locales. The guard matched whole words, so it refused `shot` and never saw `shoot` — nor `boots`, which is how "Replace the steering rack boots" and "Rust / scoring on CV boots" shipped as footwear. Two changes, both in `catalog.e2e-spec.ts`:
  - **A banned word is now a STEM plus an optional plural**, and `shoot`/`shooting`/`gaiter`/`undercarriage`/`pinch` joined `boot`/`shot`.
  - **The check reads four collections, not one** — angles, parts, damage types and repair methods. It read the angles alone, so 22 defective English source strings sat in the other three: `trim` (a haircut) → `side panel`, `gaiter` ×4 → `bellows`, `Play …` ×7 → `Free play …`, `(skid plate)` ×2 → `(underbody plate)`, `Parcel shelf / Roller cover` → `Retractable luggage cover`, `VIN plate` → `VIN data plate`, `Rear view`/`Front view` → `Rear`/`Front of the vehicle`.
  - **A qualifier may be joined by a HYPHEN as well as a space.** The space-only pattern read `number-plate light` as a bare "plate" and refused a correct string; `scuff plate` needed the allowance, and `skid plate` turned out to be a genuine defect rather than a false positive.

**The cabin is the client's ordered SEVENTEEN angles (2026-08-17), and the order is asserted as a sequence too.** His numbered reference set is `images/internal_ordered_numbered/1..17.jpg`: door by door down the left flank, the console worked through from the rear seat, the pedals, the instrument cluster with the engine running, the documents and keys, the same walk down the right flank, then the luggage area. It replaced twelve slots this project had chosen.

- **Angle ids are persisted, so three were reused rather than minted.** `interior_front` and `interior_rear` were unsided and became the LEFT views; `interior_dashboard` keeps its id AND its label, because its reference frame is the whole dashboard and the console the client named is `interior_head_unit`.
- **`interior_seats` and `interior_overview` were RETIRED.** The mobile PDF builder appends a photo whose angle id has left the catalog, so evidence in an unfinished draft is never dropped, and a mobile-side alias keeps its caption. `CATALOG_VERSION` stays `'1'`, so an installed build meets the new list only after an app update.
- **`interior_boot` reads "Luggage area", not "Boot / trunk".** Two defects in one string: `boot` is the word the pivot renders as FOOTWEAR — which the exterior labels have avoided since August — and a slash pair of English synonyms came back as the same word twice in eight locales, wholly untranslated in Turkish and half-translated in Czech. **The pivot-word check now reads every angle, not only the exterior ones**, which is the gap that let it survive.
- **Seventeen cabin angles raise the guided slot count to 34**, which is why `MAX_LISTING_PHOTOS` went 32 → 40. Interior angles stay `required: false` and are absent from `report-completeness.ts`, so nothing commercial moved.

**The English strings are the machine-translation pivot, so an ambiguous English word is a correctness bug, not a style question.** Every one of these shipped once during the 8 → 17 work and came back wrong in a double-digit number of locales: `boot` as FOOTWEAR in twenty languages (cs "kopačka", pl "but", ja "ブーツ"), `shot` as a GUNSHOT in nine, a bare `bay` as a COASTAL BAY in all 26, a bare `hood` as a garment hood, and a bare `right` as "correct" (hu "igen", it "giusto", pl "prawda"). The labels therefore read "luggage area", "engine bay" and "engine hood" — the compounds every locale renders correctly. `catalog.e2e-spec.ts` refuses a stem plus its plural outright (`boot`, `shot`, `shoot`, `shooting`, `gaiter`, `undercarriage`, `pinch`) and requires a per-word qualifier for the rest (`bay`/`hood` → "engine", `play` → "free", `plate` → "data"/"underbody"/"number"/"scuff", `gauge` → "thickness"/"paint"), joined by a space **or a hyphen**. It reads all four registers — angles, parts, damage types, repair methods — because reading the angles alone left 22 defective source strings in the other three until 2026-08-17. Hand-authored per-locale corrections live in `carsalepro-mobile/tool/l10n/overrides.json`, keyed `cat:angles:<id>`, each with a `why`.

**No catalog label or hint may carry a long dash (2026-08-20).** U+2014 and U+2013 became plain hyphens in `catalog.data.ts` and in all 31 sidecars — 127 and 148 of them — on the client's instruction, and the numeric ranges (`150–300 µm`, `15–20 %`) went with the separators. Two things follow. The mobile repo's `test/l10n/no_long_dash_test.dart` checks the EXPORTED bundle, so a re-export that loses the sweep fails there and not here; and `carsalepro-mobile/tool/l10n/overrides.json` was swept in the same change, because `apply.mjs` re-applies every value in it over machine output and would have put 27 dashes straight back. Only string literals were touched: the ~100 explanatory comments in `catalog.data.ts` keep theirs.

Angle `order` is not persisted anywhere, angle **ids are** (mobile photo kinds `exterior-<id>` / `interior-<id>`, cloud slot keys), and **an angle id must never equal a `parts` id** — the website indexes both into one flat label map, so a collision silently replaces a part label in the damages and thickness tables (asserted). `thicknessPanels` holds the **17** guided Lackdicke stations, each resolving to a real `parts` id — **the `extra_` panelId prefix is reserved** for user-added ad-hoc measurements (same idea as the `C` prefix).

**The paint walk is 17 stations in the client's dictated order since 2026-08-19, and two stations per side share one `partId`.** It grew from 13 by adding the four door sills, inserted where the client asked rather than grouped: `4 sill_rear_left`, `6 sill_front_left`, `12 sill_front_right`, `15 sill_rear_right`, so the left flank is deliberately **not** a mirror of the right. Three consequences, each of which bit once:

- **`partId` is `rocker_panel_left` / `rocker_panel_right`, shared by two stations per side**, because the painted panel a sill belongs to is one part. `sill_left`/`sill_right` are the decorative trim strips and are the wrong target. Minting four new parts would have cost 140 more strings plus four near-duplicates in the damages picker.
- **A shared `partId` breaks label resolution, and the fix lives in the mobile app.** `thicknessPanelLabel` prefers the *part* label over the station's own, so both left-hand sills rendered "Left rocker panel" — in the editor, the progress count and the PDF table. The rule is now: when a `partId` is shared by more than one station, the station's own label wins. Anything that adds a second station to an existing part inherits that behaviour automatically.
- **`thicknessPanels` was ABSENT from the pivot-word guard's `subjects` map** (`catalog_test.dart` in the mobile repo), so a panel label could say anything. It is in now, and it reads the **resolved** label through the app's own precedence rule rather than the raw field — which is how it caught `thicknessPanels.hood` ("Hood / bonnet", a bare *hood*) on a label that is currently never rendered because the part label wins. Bare *sill* is a **window** sill in most targets and bare *threshold* is an abstract limit, so the English labels qualify it: `Rear left door sill`, and `threshold` joined `bannedOutright`.

**The quality weight did not change, so an existing complete report drops from 100 to 96.** Weight 15 now prorates over 17 stations instead of 13, and a phone on the 13-panel bundle cannot repair it. That is a consequence of the expansion, not a defect — but say it out loud before someone reads it as a regression. Fields are additive — the frozen `GET /catalog` shape is unchanged. Regenerate the client + re-run the export after any catalog edit.

**`CATALOG_VERSION` is an over-the-air content push, not a tidy-up.** `GET /catalog?version=<v>` answers `{upToDate:true}` when the caller matches, and the mobile app sends the version of the copy BUNDLED in its build — so while it reads `'1'`, an installed app keeps its own catalog and picks changes up only when the user updates. Bump it and every installed build hot-adopts the new list, including any new required angle for which that build has no example thumbnail and no overlay, and every in-progress report's quality score drops at once. The 8 → 17 expansion shipped deliberately WITHOUT a bump.

**The sidecars must be COPIED into `dist/`.** `tsc` emits only JavaScript, so `src/catalog/i18n/*.json` reaches the build output solely through the `assets` list in `nest-cli.json`. It was missing there, `mergeCatalogI18n` found nothing, and — because an absent directory returns an empty report rather than throwing, which is right for one missing locale — **production served a four-locale `GET /catalog` from the day the 30-language work shipped until 2026-08-10**. Nothing noticed: the app reads its bundled copy and the website needs only de/en/ru. `catalog.i18n.spec.ts` cannot catch it (it reads from `src/`); `catalog.i18n.packaging.spec.ts` asserts the packaging rule instead.

## Downloadable PDF fonts (`src/fonts/`)

`GET /fonts/manifest` returns presigned URLs plus a SHA-256 and byte count for each CJK font face, stored under `fonts/v1/` in the reports bucket. The mobile app fetches a pack the first time it generates a Chinese, Japanese or Korean report and caches the bytes.

Three things here are decisions, not defaults:

- **Why serve them at all.** `package:pdf` embeds its own fonts and cannot use the platform's, so a CJK report needs a real ~10 MB file even though both mobile platforms ship CJK system faces. Bundling all four would add ~33 MB to an app most of whose users never generate one.
- **Why mirror instead of linking gstatic.** `fonts.gstatic.com` is unreachable from mainland China — the single largest market for the locale it would be serving.
- **Why the digest is mandatory.** A truncated TrueType file does not throw when parsed. It yields a font whose glyph metrics are all zero, and the report renders with invisible text and nothing in the logs. `scripts/upload-fonts.ts` verifies every file against the committed digest — and that its sfnt version is TrueType `glyf`, not OTF or a collection, which `package:pdf` silently mis-parses — **before** uploading any of them, so a half-published pack cannot leave the app fetching three faces of four.

The manifest is a root route alongside `/catalog` and `/legal`; the frozen mobile contract is untouched.

## Hard rules

- **Never break the mobile contract.** Don't change root routes, their `X-Device-Id` behavior, or the R2 key layout `<tier>/<deviceId>/<reportId>.pdf` (GDPR erasure in `MeService.erase` + `R2Service.deletePrefix` depend on it). Extensions must be additive (like report-sync v2 was). Legacy mobile e2e (`mobile-link`, `vin`, `quota`, `reports`, `report-sync`, `report-photos`, `me`) must stay green.
- **FREE is unlimited (since 2026-08) — but the 402 shape is still frozen.** `POST /reports` no longer caps anything: enforcement sits behind `ENFORCE_FREE_REPORT_LIMIT`, which **defaults to false** (`quota.enforceFreeLimit`, `render.yaml` pins `"false"`). Never "disable" it via `FREE_REPORTS_LIMIT=0` — Joi rejects that (`.min(1)`), because `used >= limit` would then reject the *first* report. When the flag is true, `consumeQuota()` throws exactly this and nothing else (pinned by `test/reports.e2e-spec.ts`). Since 2026-08-09 `AllExceptionsFilter` **passes through** any key a domain exception put alongside `error`/`message`, so `freeReportsUsed`/`freeReportsLimit` now reach the wire beside `{statusCode, error, message, path, timestamp}` — purely additive, and inert for the shipped Flutter app, which derives `quotaBlocked` from the 402 **status alone** (`lib/core/net/net_failure.dart:80`) and never reads the body:
  ```json
  { "error": "PaymentRequired",
    "message": "FREE-tier limit of 3 reports reached. Upgrade to PRO to continue.",
    "freeReportsUsed": 3, "freeReportsLimit": 3 }
  ```
  Keep the machinery: `DeviceQuota` is still the storage for **`isPro`** (drives the PDF watermark and the ad gate), `freeReportsUsed` still increments (with `rollbackQuota()`), `GET /quota` still returns all five legacy fields verbatim — the mobile freezed DTO declares them non-nullable `int`s — plus the additive `freeLimitEnforced`, and `Report.tier` still drives the R2 key layout. Don't churn any of it.
- **The photo manifest's ORDER is the showroom's gallery order, and it is the catalog's walk-around.** Every reader takes the first N entries — the detail page, the mirrored public-bucket subset, the advert thumbnail. It used to be written `ORDER BY kind ASC`, which is alphabetical, and `checklist-`/`damage-` sort ahead of `exterior-`: a well-documented inspection opened its advert on a scratch macro and, past a dozen damage photos, showed **no picture of the car at all**. `src/catalog/catalog-photo-order.ts` owns the rule (`angleForKind`, `comparePhotoKinds`) and is a plain module rather than a provider precisely so `reports/` and `listings/` cannot hold two copies of it. `manifestPhotoRefs` applies the same sort **on read and before truncating**, which is what repaired every already-stored manifest at deploy time without a data migration — do not "optimise" that away. `angle` (the bare catalog id) is written beside `kind`; it had been in the read DTOs since report-sync v2 and populated by nothing.
  - **Anything that changes the mirrored subset must widen `erasePublicPhotoObjects` too.** The subset is "the first `MAX_LISTING_PHOTOS` entries in manifest order", so moving either the cap or the order strands objects mirrored under the old rule — a permanent, CDN-cached public photograph of a car whose owner asked to be erased. It derives its keys from the WHOLE manifest for that reason.
- **Report sync v2 invariants** (`src/reports/`): `CSP-<uuid v4>` codes are the create-idempotency key — re-posting the same code from the same device returns the existing report and **never consumes quota twice** (partial unique index `report_code_uuid_unique` backs the cross-device 409). `reportData` with `reportSchemaVersion: 1` is validated **before** quota is consumed (a 400 never burns a credit) via `report-data.validator.ts` — lenient, unknown keys allowed. `PUT /reports/:id` is quota-free. Photo uploads (`POST /reports/:id/photos/upload`, multipart) are compressed server-side by `photo-processing.service.ts` (sharp, 1920 px, mozjpeg q80, 2-transform semaphore) and slot-keyed `(reportId, kind, position)` with a content-hash short-circuit; `photosManifest` is mirrored from `ReportPhoto` rows so website consumers stay untouched. Photo keys live under `report-photos/<deviceId>/<reportId>/`.
  - **The device started sending BIGGER photographs on 2026-08-21, and the 1920 px reduction is now doing real work.** The mobile capture stream used to be `ResolutionPreset.high`, so a saved frame was about 720 px across and this pipeline passed it through almost untouched. The app now asks for the whole 4:3 sensor array (it was cropping a quarter of its own horizontal field away) and caps the saved frame at **2048 px**, chosen to sit just above the 1920 px here so nothing is lost and nothing is wasted. Roughly 300 KB per photo instead of 50 KB, against a 15 MB per-file ceiling in `reports.controller.ts` - two orders of magnitude of headroom, so no `413` became reachable. **No backend change was needed**: slots are still keyed `(reportId, kind, position)` and `CATALOG_VERSION` is still `'1'`. Do not "optimise" the sharp step on the assumption that incoming frames are small.
- **`reportData` v1 array caps are sized for the worst report, not the average one** (`dto/report-data-v1.dto.ts`): `photos` **600**, `damages` **400**, `checklist` 200, `thickness.panels` **120**, `recipients` 20, `wheels` 4, plus a **4 MiB** payload cap in the validator and a **6 mb** JSON body-parser limit in `main.ts`. Raised on 2026-08-17 because the client could not save a report with many photographs; the old ceilings were only a few times the worst real report, and a payload the server refuses is a report an inspector cannot save.
  - **The body-parser limit must stay strictly ABOVE the payload cap**, so an oversize report is refused with a named 400 rather than a raw parser error. Photographs and the PDF never travel in that body — photos are multipart, the PDF goes to a presigned URL — so this limit bounds structured JSON only.
  - **Every cap is a RAISE, so the deploy order is backend first, app second.** An older app is unaffected in both directions; a newer app against an older API is the one failure mode, and it is exactly what the mobile `SAVE-05` message names ("install the newest version"). It reads the 400 `report_data_too_large` code and the 413.
  - **The photo-upload throttle is 120/min** (was 40). Not a concurrency grant: the app uploads photographs strictly sequentially, so at 40 a 100-photo report hit 429 on the 41st and its cloud copy never completed in one pass. Still bounded by 15 MB per file, one file per request, per-device keying and the sharp two-transform semaphore.
- **`body-parser` failures are 4xx, not 500.** It predates Nest and throws a plain `Error` carrying `status`/`statusCode` and a `type` of `entity.too.large` or `entity.parse.failed`. `AllExceptionsFilter` did not recognise it, so a body over the limit answered **500** — "the server has a problem" for something the client sent, which sends an inspector looking at their own report. `asBodyParserError` maps it; the body is still masked, because a 4xx from the parser carries nothing worth leaking and the status IS the message.
  - **`recipients` is retired on the client and kept here anyway (2026-08-14).** The mobile app removed the e-mail recipient feature outright, so nothing sends the key any more. The DTO keeps it optional because an older installed build still can, and dropping it would turn those uploads into a 400 with `forbidNonWhitelisted`. Do not read it in new code. Hitting a cap is a 400 `invalid_report_data`, which **blocks the mobile Finish flow** — raise a cap before it can bite, never tighten one.
- **Money in `reportData` is plain EUR numbers** — a documented, contained deviation from the integer-cents rule (archival inspection JSON, never ledger input).
- **Money is integer cents.** No floats. All fees/tariffs come from `PlatformSetting` via `SettingsService.getCents`/`getNumber` — never hardcode amounts.
- **Order lifecycle goes through the state machine** (`src/orders/order-state-machine.ts` `canTransition` + `OrdersService.transition`). Refunds/transfers/payouts fire only from legal transitions. The per-order contract auto-renders on the `ASSIGNED` transition (wrapped so it can't break assignment).
- **Auth surface:** website routes live under `@Controller('api/v1/...')`; the global `JwtAuthGuard` enforces JWT only for `/api/v1` and re-loads the user from the DB each request (ban/erasure/role/KYC are authoritative from the DB). Use `@Public()` to opt out, `@Roles(Role.ADMIN)` for admin routes (every `api/v1/admin/*` controller must carry it), `@CurrentUser('id')` for the caller.
  - **`@Public()` is a FULL bypass — it returns before `req.user` is ever populated.** So `@CurrentUser('id')` on a public route is `undefined` even when the request carried a perfectly valid Bearer token. That is right for login and the webhook, and wrong for a route that is open to visitors but still wants to know who is asking. Pair it with **`@OptionalAuth()`** (`POST /api/v1/orders/quote` is the only user today): the guard then resolves the caller best-effort and **never throws** — a stale token means anonymous, not 401. `@OptionalAuth()` without `@Public()` does nothing, so it cannot weaken a protected route. Without it, making the quote public silently dropped both the waitlist entry and the self-assignment exclusion for every signed-in caller.
- **One named throttler must not cap the whole app.** `ThrottlerGuard` evaluates **every** configured throttler on **every** route, so the `lookup` bucket (20/min, meant for unauthenticated VIN/report lookups) capped the entire API — mobile photo upload died at exactly 20 and no full report could finish its backup in one pass. `NamedThrottlerGuard` (`src/common/guards/named-throttler.guard.ts`, registered in `app.module.ts`) skips any non-`default` throttler a route did not explicitly request via `@Throttle`. Adding a third named throttler needs no change; forgetting the guard does.
- **CORS is a list.** `WEB_ORIGIN` is the **canonical** origin (used to build absolute URLs; if it holds a comma-separated list the FIRST entry is canonical) and `CORS_ORIGINS` is purely additive. Resolution is pure and tested in `src/config/cors.ts` — `main.ts` is unreachable from Jest, which is why the rule deciding who may call the API had no test and shipped allowing exactly one origin.
- **Prisma over raw SQL — except PostGIS.** Geography columns are `Unsupported`; do geo I/O with parameterized `$queryRaw`/`$executeRaw` (`Prisma.sql`/`Prisma.join`) — never string-interpolate user input.
- **Stripe** runs MOCK when no key OR `NODE_ENV==='test'`. The webhook (`/webhooks/stripe`, `@Public`, raw body) verifies the signature, then **claims** the event (`StripeWebhookEvent.status='claimed'`), handles it, then marks it `processed`; an exception deletes the claim so Stripe's own retry picks it up, and a claim older than five minutes may be stolen. Writing the row only *after* success — the old behaviour — makes a **replay** a no-op but does nothing about two **concurrent** deliveries of the same event: both found no row and both ran the handler, which for a capture or a transfer means twice.
- **A payout account's COUNTRY is chosen once and can never be changed; its LEGAL FORM is the inspector's to state, and unanswered means unanswered (2026-08-19).** `createConnectedAccount` sent `country: 'DE'` and `business_type: 'individual'` as literals, so the platform could onboard exactly one population — a German natural person or sole trader. A company anywhere could not be paid at all, and the reason was invisible: Express onboarding does not offer the company form to an account that already declares itself a natural person. `resolveConnectAccountParams` (`src/inspector/connect-account-params.ts`) owns the rules and its spec is the specification.
  - **Precedence is request → stored → `STRIPE_CONNECT_DEFAULT_COUNTRY`.** The default is last, not first, so a client sending no body behaves exactly as it did before the fields existed, while an inspector who answers is believed.
  - **The country lock answers 409 `connect_country_locked`, and names the stored country.** Stripe has no API to move an account. Ignoring the mismatch is the invisible failure: onboarding opens, the inspector submits documents for the wrong country, and it surfaces as an unpayable account weeks later. An account with **no** stored country is read as belonging to the platform default — that is what the old code sent and what the `20260819100000` backfill writes, and the two must keep agreeing.
  - **A null `business_type` is passed to Stripe as an ABSENT field, never as a default.** Express then asks, which is the only answer that is right for every applicant. Changing it later is attempted at Stripe and, when Stripe refuses (verification done), is logged and DROPPED — the column must keep describing the account as it actually is, or a payout is held for a disagreement nobody can see.
  - **There is no list of supported countries in this repo, deliberately.** Which countries Stripe opens is Stripe's answer at the moment of the call; a roster here would refuse a country the day Stripe adds it. The DTO checks the SHAPE (two letters), and Stripe's refusal is mapped onto `connect_country_unsupported` with the country named. Onboarding outside the platform's own country also needs cross-border payouts enabled — prove a country with `scripts/stripe-connect-smoke.mjs`, not with an inspector.
- **Order money is AUTHORIZED on creation and CAPTURED when an inspector accepts** (`capture_method: 'manual'`). No `OrderStatus` expresses this — `PAID` already means "the customer's money is committed", and held-versus-taken is a *payment* fact (`Payment.status`: `pending → authorized → succeeded`, or `cancelled` when the hold is released; `authorizedAt`/`capturedAt`/`canceledAt`). Adding an order status would have meant rewriting every transition guard for something the state machine does not care about. Rules that follow from it:
  - **An order is never `ASSIGNED` with uncaptured money.** `acceptOffer` claims the order with a single conditional `updateMany`, captures, and only then transitions; a retryable capture failure undoes the claim and returns the offer, a fatal one cancels and releases. `adminAssign` captures too — it reaches `ASSIGNED` by another door.
  - **`ASSIGNED → UNASSIGNED` is deleted from the state machine.** Nothing performed it, and it would return a *captured* order to the search pool where the expiry cron would try to release a hold that no longer exists.
  - **`order.search_expires_at IS NULL` must never be backfilled.** Null means "created before manual capture, money already charged, no hold to release" — it is the only thing protecting those orders from the expiry cron.
  - Stripe must be subscribed to `payment_intent.amount_capturable_updated`, `.canceled` and `.payment_failed`. Under manual capture `payment_intent.succeeded` fires at *capture*, not at payment.
- **A `Refund` row means money went back, or is still trying to.** `settleRefund` never throws: nothing charged → an `OrderEvent` and no row; an uncaptured hold → released, `authorization_released`, **still no row**; a captured payment → upsert on `(orderId, reason)`, parked with backoff on rejection. A throw here used to abort `cancel` with the money still taken, and left `resolveDispute`'s `Dispute` row OPEN in the admin queue for ever. Refunding also **revokes what was bought** — a `ReportPurchase`, and a `VinHistoryPurchase` that reached `ready` (that product is retired, but old rows can still be refunded and must still say so; one that never reached `ready` granted no access, and overwriting it would destroy `failureReason` and claim a refund that may itself have failed).
- **The order gate asks WHICH elements a report contains, not how good it scores** (since 2026-08-13; `src/reports/report-completeness.ts`, applied by `OrdersService.assertReportComplete` from both `attachReportByCode` and `ReportsService.create`). Required: every exterior angle photographed, all **17** paint panels with a reading **and** a `thickness-<id>` photo, both calibration shots (`zeroproof`, `zeroproof-al`), and 4 wheels each with a photo, `treadMm`, `dot` and `sizeSpec`. A score is a weighted average, so it let a whole missing family be paid for by another — a report with no wheel data at all cleared 90 on the strength of its exterior walk. The evidence is the payload's own `photos[].kind` manifest, because the gate runs inside `POST /reports` before any file is uploaded and no `ReportPhoto` row exists yet.
  - **`report_quality_too_low` no longer exists.** The refusal is **`report_incomplete`** (still 409), and it carries `missing` — the structured gap list — plus `exteriorAngleCount`, `qualityScore` and `minQualityScore` beside `error`, which `AllExceptionsFilter` spreads onto the wire. A bare code the client cannot turn into "the rear and one wheel" sends the inspector back to the car with nothing to go on. `report_quality_unknown` is unchanged in code and meaning but its **trigger moved**: it now fires when there is no structured `reportData` at all (an old app build), not when `qualityScore` is null.
  - **`minReportQualityScore` kept its name and now under-describes what it does.** Only its SIGN is read: `> 0` runs the gate, `<= 0` disables it entirely — the same emergency lever as before, and `admin-settings.controller.ts` still bounds it at 100. It is no longer a threshold and nothing compares a score to it; the score is still stored and still displayed. The name survived on purpose, because renaming it would have cost a migration, a seed change, an admin control and an order-DTO field — and would have cost the lever a deploy at exactly the moment it is needed. So **the 87/81 window is gone**: it described a threshold that no longer exists, and the setting's value between 1 and 100 changes nothing.
  - **Old reports stay closable through a legacy amnesty, not through a tuned number.** `resolveRequiredAngles` judges a payload that covers the pre-2026-08-10 set of 8 angles and shows no sign of knowing the newer ones against those 8. Showing even ONE newer angle proves the build knows about them, so the current set applies — otherwise an inspector could opt out of the expansion by skipping shots. This is why growing the walk-around no longer needs a matching settings change.
  - **`resolveRequiredPanels` is the same amnesty for the paint walk, and it is why the 13 → 17 expansion could ship at all** (2026-08-19). Unlike the angles, the panels had **no** escape hatch: a station was required unconditionally, so the moment the backend deployed with 17 panels every phone still on the 13-panel bundle would be refused with eight elements its UI cannot collect — and `CATALOG_VERSION` stays `'1'`, so an installed build keeps its bundled 13 until the user updates the app. The rule mirrors the angle one: a payload that names **no** sill is judged against `LEGACY_THICKNESS_PANELS_13`, and naming even one proves the build knows the new list, so the current 17 apply. `mentionedPanels` is collected from the readings **and** from `thickness-<id>` photo kinds, because a station can be evidenced by either. **Deploy this before the app, never after.**
  - `GET /orders/:id` `reportRequirement` carries `minQualityScore` + `currentQualityScore` plus four OPTIONAL counts — `gateEnabled`, `exteriorAngles`, `thicknessPanels`, `calibrationPhotos`, `wheels`. Optional so the website can deploy in either order; they are data, not copy, so growing the walk-around needs no website release.
  - **Changing the seeded default alone does nothing to production.** `prisma/seed.ts` upserts settings with `update: {}` and Render runs `prisma migrate deploy`, never the seed. Move it with a guarded `UPDATE ... WHERE value = <old>` migration, like `20260810120000_lower_min_report_quality_score`.
- **Notifications are non-fatal** — `NotificationService.notify` must never throw into a domain flow; in `NODE_ENV==='test'` it dispatches inline so e2e can assert rows. The scheduler (`src/scheduler`) is gated off when `NODE_ENV==='test'` or `SCHEDULER_ENABLED='false'`.
- **Secrets** come from `ConfigService`, never source or logs. KYC documents are served only via short-lived **signed** URLs (`R2Service.createPrivateSignedUrl`) — never a public URL. Mask device/user ids in logs (`mask()` helpers).
- **No schema edits without a migration.** Migrations under `prisma/migrations/` are part of the contract — never edit a committed one. **`prisma migrate diff` proposes `DROP INDEX` for the three PostGIS GIST indexes on every single run** — grep the generated SQL for `DROP INDEX` and strip those lines before committing, then re-verify with `SELECT indexname FROM pg_indexes WHERE indexname LIKE '%location_idx'` (three rows).
- **Money that reaches a client comes from `SettingsService.getPriceCatalog()`** (integer cents). The website must never hardcode a price or bake one into a translation file.
- **A notification whose payload carries a live credential must not create an inapp row** — `GET /api/v1/notifications` returns the stored payload, so an in-app copy of a password-reset link turns a borrowed session into a permanent takeover. See `SECRET_BEARING_TYPES`.
- **KYC objects go through the `kyc*` methods on `R2Service`, never the general ones** — `putObject` and `createPresignedDownloadUrl` both hardcode the reports bucket, so a call site that looks correct would put identity documents next to paid PDFs. **The browser never writes to that bucket.** Uploads are multipart through `POST /api/v1/kyc/applications/:id/documents/upload`; the presigned route is deleted, and CORS must never be added to the KYC bucket — that is a browser-reachable write path into the identity store, not a fix. The content type comes from the multipart part (a body field guarded by `if (contentType && …)` was bypassed by omitting it) and is corroborated against magic bytes. One document per kind, `@@unique([applicationId, kind])`: appending meant every reader picked one non-deterministically, so a reviewer could judge an applicant on a document they had already replaced.
- **Revocation must not be undone by registering again.** A rejection is the only way to take an inspector's access away, and approval is automatic, so the hold on a re-application is the whole of the control. That hold was keyed by `user_id` (DEN-239), which a second registration resets — the same person, a new account, the same four files, back in within a minute. `KycDocument.sha256` (DEN-249) gives the FILES an identity that survives the account: `submitApplication` holds an application whose documents were already seen on a `REJECTED` one under any other user. Hash the SOURCE bytes, never the stored object — an image is re-encoded before it is written, so the object's digest depends on the sharp build. The row outlives the object (`purgeOldDocuments` clears the bucket and keeps the row), which is what makes the check work after the retention window and keeps it a digest rather than a document. **It recognises the same FILE, not the same person:** a re-crop or a second photograph defeats it, and it must never be described as identity verification.
- **A document the platform cannot read must never hold an application.** `KycDocument.idNumberHash` (DEN-250) closes the gap the file hash leaves: photograph the same passport again and every byte differs, while the number in the machine-readable zone does not. The MRZ is ICAO 9303, not a German feature - TD1/TD2/TD3 cover every passport and every EU identity card - but a national card from outside the EU may carry none, and a bad photograph reads as nothing. **Every failure path stores NULL and NULL matches nothing**, so the applicant behaves as they did before the check existed. The opposite rule ("unreadable means held") refuses work to honest people for owning the wrong bureaucracy. `parseMrz` accepts a zone only when three ICAO check digits agree, which is why there is no confidence threshold to tune; the readers measure a PREFIX and not the whole line, because the filler run is exactly what a recogniser turns into `L` (a specimen passport read back as a 47-character name line above a perfect data line, and an exact-width rule threw the good number away). Hash the state and the code with the number - a document number is unique within a country, not across them - and pepper it, because after `purgeOldDocuments` these digests are all that is left of the document.
  - **The pepper cannot be rotated silently, so the digest carries `ID_HASH_VERSION`.** `KYC_ID_HASH_PEPPER` reads as an empty string when unset, so setting it for the first time - or changing it - makes every stored digest disagree with every new one: the comparison then matches nothing, the application is approved, and no error and no log line says why. The version prefix does not repair the old rows and is not meant to; it makes the break VISIBLE, and a query can count each generation. The startup check warns on a missing pepper in production and never prints it.
  - **The read has a DEADLINE, and one worker serves every upload.** `tesseract.js` queues all jobs onto the single worker `MrzOcrService` keeps, and the read runs inside the applicant's upload request - so a recogniser that never returns held that request open AND every later KYC upload in the process behind it. `READ_DEADLINE_MS` frees the request; passing it is an ordinary failure and gives `null` like any other. The losing side of the race is still a live promise, so it is caught - otherwise a late rejection is an unhandled one. Unavailability is a COOL-DOWN (`retryAfter`) and not a permanent flag: a network blip while the language data was first fetched used to cost a redeploy.
  - **The TD2 reader asks for the true 36-character width.** It asked for 28, a TD1 line is 30, and `parseMrz` tries every TD2 read before any TD1 read - so an identity card reached the wrong reader first and cut its "document number" out of the date of birth. The three check digits refuse almost all of those, which is worse than refusing none: it shipped looking correct. The prefix rule still applies past the fixed width, where the filler is.
  - **The retention period is PUBLISHED, not copied.** `KYC_RETENTION_DAYS` lives in `kyc.constants.ts`, the purge reads it, and `GET /api/v1/settings/public` emits it as `kycRetentionDays` - because the website prints it to an applicant at the moment they hand over an identity document. It was a literal here and a second literal in the frontend repo. A stale price misinforms a buyer; a stale retention period is a promise about someone's personal data that nothing keeps.
  - **The admin queue selects three user fields and skips deleted users.** `include: { user: true }` read `passwordHash` and `totpSecret` into memory for up to `KYC_QUEUE_MAX_LIMIT` applicants per page. They never reached the wire and never needed to leave the database either.
- **`R2_PUBLIC_URL` is RETIRED and fails the production boot.** It reads like a per-feature setting and is a global short-circuit inside `createPresignedDownloadUrl`: set it and every private object in the reports bucket — paid inspection PDFs included — resolves to a permanent unsigned URL, with nothing logged and nothing broken-looking. Public images come from a **separate bucket** (`R2_PUBLIC_*`), because publicity in R2 is a property of the bucket and a "public prefix" cannot exist. `ListingPhoto.bucket` records where each object lives, so the feature ships dark: unset the vars and everything returns to signed URLs.
- **A boot-time self-check (`src/health/startup-check.service.ts`) fails the start on a silently-wrong environment** — a BOM or stray quoting in a secret, a KYC bucket equal to the reports bucket, a CORS list with no https origin. Four of the nine blocking production defects were env values, and not one failed a build, a test or `/health`. It never prints a value, only `MISSING` / `set (len 64)` / `has BOM`. A third party being unreachable is deliberately NOT fatal (Render would loop the deploy); `STARTUP_CHECK_STRICT=false` and `ALLOW_SHARED_KYC_BUCKET=true` are the documented escapes. **This reverses the earlier "R2_KYC_* must not fail the boot" decision** — set those vars on Render *before* deploying. `GET /health` is untouched (it is `healthCheckPath`); details live on `GET /health/startup`.
- **`null` is not `0`, wherever a count reaches a client.** `0` is a claim somebody made; `null` means no such number is published. The VIN preview is where this was learned - its counters were hardcoded zeros, so a card told visitors a car was clean on the strength of never having looked - and the rule outlived the feature. Fix it in the contract that produces the number, not at the call site.

- **Mobile PRO is a ONE-TIME purchase, and there is no subscription anywhere in the mobile tier (2026-08-19).** The product is `carsalepro_pro_lifetime` — **Non-Consumable** on Apple, a **managed in-app product** on Google. Three things follow, and each is a trap in the opposite direction:
  - **`GOOGLE_PLAY_SUBSCRIPTION_IDS` must stay empty.** `google-validator.ts` routes an id in that list to the subscriptions endpoint and everything else to `/purchases/products/`. A well-meant entry there sends the lifetime id to the wrong endpoint and every purchase 404s. A spec now pins that the lifetime id routes to `/purchases/products/` under the default empty list, so a future env change fails a test instead of a customer.
  - **`quota.service.ts` already grants a permanent entitlement** — `DeviceQuota.isPro` with no expiry column. Do **not** add expiry handling; a one-time unlock has nothing to expire.
  - **The app calls `buyNonConsumable`, which is correct and must not change.** It reads like the thing to "fix" when a product stops being a subscription, but non-consumable is exactly what a lifetime unlock needs: restorable after a reinstall, and impossible to buy twice.
- **`IAP_BUNDLE_ID` and `GOOGLE_PLAY_PACKAGE_NAME` both defaulted to a package that has never existed** (`com.carsalepro.app`, against the shipped id), and because the Google name falls through to the Apple one, **both** stores' server-side validation pointed at nothing. It was invisible because `IAP_VALIDATION_MODE` defaults to `client-trust` and never contacts a store. Both defaults are corrected, and **the retired value is now IGNORED wherever it comes from** — `configuration.ts` (`bundleIdFromEnv`) drops it from `IAP_BUNDLE_ID` and `GOOGLE_PLAY_PACKAGE_NAME` alike and resolves the shipped id, because a package that no store publishes cannot be a correct answer. **`RETIRED_BUNDLE_IDS` is a LIST, and it holds two ids since 2026-09-04:** the app renamed from `us.designkey.carsalepro` to `net.carsalepro.app` before its first Play upload, so the previous id is retired on the same grounds. The startup check reports the stale variable as a **warning** (`iap.bundle`, carrying the id actually used), not as a refusal: it was FATAL in `server` mode until 2026-08-21, and Render's env still held the retired value, so a mobile-only setting took the entire API down on boot and could only be cleared from a dashboard. Any OTHER value is believed — a staging or second-app id must keep working.
- **The static legal documents serve ENGLISH when they cannot serve the asked-for language, not German (2026-08-19).** `resolveLang` in `legal.controller.ts` fell back to `'de'`, and the mobile app sent the raw language code, so a Greek phone asking `?lang=el` matched nothing and read the privacy policy **in German** — 31 of 35 locales did. The company block in `legal.content.ts` is also filled now (CarSalePro LLC, 1023 E Lincolnway, Cheyenne, WY 82001, support@carsalepro.net) and `legal.content.spec.ts` asserts **no `[` survives in any rendered section in any `LEGAL_LANGS`**, because the same unfilled placeholder text had shipped in two repos at once. The mobile app now links the website's canonical pages rather than this route; keep the route, the store listings point at it.
  - **`COMPANY` / `ADDRESS` / `EMAIL` in `legal.content.ts` are now read by a MOBILE test (2026-09-01), and changing them silently breaks it.** The mobile report prints the same three values on every page (`carsalepro-mobile/lib/core/brand/letterhead.dart`, `PlatformIdentity`) - in the page FOOT, and again in the imprint block that closes the report. It printed them in the page-one HEADER as well until 2026-09-03, when the client asked for only the mark up there; the coupling below is unchanged by that, because the values and the test that reads them are. `carsalepro-mobile/test/core/pdf/letterhead_test.dart` parses THIS FILE and fails when the two disagree. There is no shared package between the repos, so a parser over the source is the only coupling available — but the reason for it is not tooling: a report naming a different address from the Imprint the store listings point at is worse than one naming none. If the entity moves, both repos change in the same commit or the mobile suite goes red on the next run.
    - **That is exactly what happened on 2026-09-02**, and the coupling did its job. `EMAIL` became `support@carsalepro.net` on the client's instruction; the mobile change alone would have turned `letterhead_test.dart` red, which is the intended behaviour and not a nuisance. `ADDRESS` was NOT touched - the client's own §1.6 text says `1021 E Lincolnway, 10416` and he decided `1023` is acceptable, so the website Imprint's `Provider` section still disagrees with its own `Mailing address` section. Do not "correct" one of the two here without him.

## Adding a website feature

It belongs here, under `/api/v1`. Add a module (controller `@Controller('api/v1/<feature>')` + service + DTOs with class-validator), wire it in `app.module.ts`, reuse `SettingsService` / `OrdersService.transition` / `StripeService` rather than duplicating money/state logic, add a `*.e2e-spec.ts` (≥ the coverage of sibling suites), and keep the mobile contract untouched.
